# Runtime topology

Ternlux has two cooperating layers.

## The interactive layer

This is what you see and click on: the workflow canvas, the node
configuration forms, the chat assistant, the connections list, the Data
Explorer, the execution monitor, and the settings screens. It builds and
edits workflows but never holds your secrets and never talks directly to
your databases.

When you ask Ternlux to do anything that touches a credential or runs a
piece of generated logic, the interactive layer asks the background
engine to do it.

## The background engine

Always running while Ternlux is open. It is responsible for:

- Keeping your AI provider keys and connection credentials encrypted at
  rest.
- Loading the available connectors and AI skills.
- Talking to external systems on your behalf — running queries, fetching
  files, calling APIs, embedding text, upserting vectors.
- Calling AI providers to generate operations, plans, and reviews.
- Watching for schedules and file-system changes, and starting workflows
  when they fire.
- Executing nodes in order, tracing every statement, and writing the
  result of every step into the execution history.

## What's stored locally

Inside your user data directory, Ternlux maintains:

- `llm-config.dat` — your AI provider keys, encrypted.
- `db-credentials.dat` — the secret parts of every saved connection
  (passwords, tokens, API keys), encrypted, keyed by connection id.
  Both files are written owner-readable only.
- A workflows store with every workflow you've created, plus its version
  history (up to 50 versions per workflow, each a full snapshot).
- A connections store with the public parts of every saved connection
  (name, type, host, the tables a file connection owns, and the *names*
  of any key/value credentials — never their values).
- An executions store with the full history of every run, including the
  per-node trace.
- A chat sessions store with your conversations with the assistant.
- `workflow-data/<workflowId>.duckdb` — one DuckDB database per
  workflow, holding every table its nodes materialise.
- `workflow-code/` — the SQL, JavaScript and Python each node carries,
  as ordinary files on disk (see [Externalized node code](workflow-code.md)).
- Two Data Explorer stores: the worksheets you have open per connection,
  and the statements you have run (500 per connection).

The files your workflows read are not among these. A local file stays
where you put it and is read in place; nothing is copied into the app.

Your workflow data is not uploaded to Ternlux's servers; it leaves your
machine only when you direct it to — to the databases, cloud storage,
REST APIs, and AI/embedding providers you connect, and to the services
the app itself uses (signing in, downloading plugins, and opt-in usage
analytics).

## How communication is shielded

Generated operations use placeholders for sensitive values. A REST API
fetch function generated by the AI references the connection's base URL
and credentials by symbolic name (`{{BASE_URL}}`, `{{X_API_KEY}}`), not
by literal value. The literal values are filled in only inside the
background engine, in the moment before the function is evaluated — and
the resolved source is deliberately never logged. The interactive layer
therefore never holds a decrypted key, and saved workflows never contain
one either, even if you share the workflow file.

The same rule holds for the assistant: it sees connection names and
key *names*, never values, and the one way it can make an authenticated
request is to generate a function that resolves the credential itself
while it runs.

## Telemetry

Ternlux can record anonymous, opt-in telemetry about which operations
are used and how long they take. It is off by default and is toggled
from the settings screen and the terms-and-conditions flow. There is no
persistent device identifier — only a random session id that resets on
every launch — and the payload is limited to an allowlist: the IPC
channel name, a duration, success or failure, and a few safe properties
such as the AI provider in use. Prompts, queries, rows, file paths and
credentials are never included, and error text is collapsed to a safe
label.
